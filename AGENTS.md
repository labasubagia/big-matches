# Repository Guidelines

## Project Overview
Big Matches is a React app with three routes — Overview, Teams, FAQ — that shows football fixtures *only* between teams in a user-selected list (mutual pairings). The FAQ route documents which competitions the Football-Data.org free plan covers (12) and which need a paid tier (UEFA Europa League and domestic league cups). Match data comes from the Football-Data.org API; teams are selected on the Teams page, and any match where either side isn't selected is filtered out. The Overview page has an always-visible filter bar whose date-range and club controls open popovers — date range (default 30 days) and an optional club filter (mutual pairings among the selected clubs; a single club matches against any globally selected team) — applied live; matches in the past get a light-gray background, all other rows are white, and matches whose kickoff time is undecided (TBD) show the time text in orange. Pages show a "Fixtures <from> → <to>" heading; finished matches show their score inline between the club names (e.g. `Inter 2 v 1 Barcelona`), with the winner's score in orange and all scores bold.

## Architecture & Data Flow
- Static data generated by CI (`scripts/provider/index.ts`, default provider Football-Data.org) → imported as JSON at build time; no runtime API access.
- User team selection lives in the browser (localStorage), is set on the Teams page (teams grouped by competition, selected teams highlighted), and is applied client-side as a pure filter over the fetched matches.
- Teams are derived from each competition's team rosters (`/competitions/{code}/teams`, free tier) and cached stale-while-revalidate; Overview renders the filtered matches via a shared `MatchList`.
- Data providers are swappable via a common interface in `scripts/provider/index.ts` (`DataProvider`: `fetchTeams(code)` / `fetchMatches(code)` / `season()` / `defaultCompetitionCodes`); implementations sit in the same `scripts/provider/` directory. Select one with `DATA_PROVIDER` env (`footballdata` default; `thesportsdb` also registered). **Exactly one provider is active per data-generation run** — the orchestrator resolves a single provider from `DATA_PROVIDER` and builds the whole `fixtures.json` (teams + matches) from it; there is no mixing, cross-provider fallback, or per-competition provider switching. Providers own their transport (auth, rate limiting, error retry). Competition codes are configurable via `COMPETITION_CODES` env (comma-separated); when unset each provider's `defaultCompetitionCodes` applies (`footballdata`: `PL,PD,SA,BL1,FL1,CL`; `thesportsdb`: `EL,FAC,ELC,CDR`; thesportsdb also accepts `CL`, `PL`, `PD`, `SA`, `BL1`, `FL1`, `CIT`, `DFB`, `CDF`).
- TheSportsDB free tier (`thesportsdb`, key `123`, no signup; optional `THESPORTSDB_API_KEY` env override) caps the team-list endpoint at 10 rows and only indexes clubs under their primary league — so the provider resolves European competitions (CL/EL) via known league ids and builds full rosters from each season's matches.

## Key Directories
- `src/routes/` — file-based routes. Adding a file here regenerates the routing tree automatically.
- `src/lib/` — core application logic: the pure filtering function (with its test) + the committed data placeholder (`fixtures.json`).
- `src/components/` — shared UI (`MatchList`, `MatchFilters`), shadcn primitives under `src/components/ui/` (button, input, popover, calendar, command), and the date-range picker / multi-select combobox powering the Overview filter.
- `src/config/` — competition / default-selection configuration.
- `scripts/` — CI data generation (`scripts/provider/index.ts` orchestrator + `provider/` implementations, run via native Node TS type-stripping) + post-build PWA generation (`generate-sw.ts`: Workbox-based service worker via `injectManifest`).
- `.github/workflows/` — CI checks + deploy (data generation, build, publish; post-deploy Lighthouse perf gate) + **PR Agent** (`pr-agent.yml`: Codium-ai/pr-agent auto-review on PRs, wired to a 9router OpenAI-compatible endpoint via `OPENAI_COMPATIBLE_URL` var / `OPENAI_COMPATIBLE_KEY` secret; model `openai/mercury-3` with `handle_push_trigger` + `push_commands=["/describe","/review","/improve"]`).

## Development Commands
Package manager: **npm** (lockfile `package-lock.json`).

| Command | Action |
|---|---|
| `npm install` | install dependencies |
| `npm run dev` | local dev server (no typecheck) |
| `npm run build` | production build (emits Workbox service worker via `scripts/generate-sw.ts`), then full TypeScript typecheck |
| `npm run preview` | preview the production build |
| `npm test` | run the test suite once |
| `npm run data:gen` | regenerate `public/fixtures.json` from the Football-Data API |

Setup: copy `.env.example` to `.env` and set the Football-Data.org API key.

## Code Conventions & Common Patterns
- **TypeScript**: type-only imports and exported types; full strict mode enabled (`strict`).
- **React**: functional components with typed props; interactive controls use shadcn-style components (`src/components/ui/`, plus `react-day-picker` + `cmdk` + radix popover) and all styling uses Tailwind CSS v4 utilities (theme tokens in `src/styles.css`, incl. `text-winner` for the winner/TBD orange). No CSS modules, no inline style objects.
- **Routing**: TanStack Router file routes; the route loads static `fixtures.json` (no server functions).
- **Naming**: constants in UPPER_CASE; small module-level helpers, camelCase.
- **Error handling**: fail loudly on API errors (throw); tolerate/ignore non-critical failures (e.g. localStorage, a single failed competition); log a dev warning for suspicious data.
- **Patterns**: derive filtered view with memoization; keep pure logic separate from UI and unit-test it.
- **Commits**: Conventional Commits enforced by commitlint via the husky commit-msg hook (types: `feat`, `fix`, `chore`, `docs`, `test`, `refactor`, `style`, `perf`, `ci`, `build`, `revert`).

## Documentation Drift
- Every change MUST be checked for documentation drift: if it affects any documented behavior, command, config, or convention (including this file), update the affected docs in the same change.
- This file is the source of truth for repo conventions; keep it accurate when conventions evolve.

## Merging
- Do NOT merge any pull request without explicit user permission.
- PR Agent review findings MUST be resolved before merge: fix the issue and resolve the thread; if a finding cannot or will not be fixed (e.g. reviewer misread or intentional design), reply on the thread with the reason, then resolve it. No unresolved review threads may remain on a PR at merge time.

## Important Files
- `src/router.tsx` — app router setup.
- `src/routeTree.gen.ts` — **auto-generated** by the router plugin during dev/build. Do not edit.
- `scripts/provider/index.ts` — CI data generation orchestrator (teams weekly, matches daily) behind a provider interface; downloads, resizes, and self-hosts team crests as WebP into `public/crests/`, so pages load entirely same-origin. Add a provider by implementing the `DataProvider` contract in the same directory and registering it in `PROVIDERS`.
- `scripts/provider/README.md` — per-provider limitations (free-tier caps, rate limits, known gaps). Read before choosing `DATA_PROVIDER`.
- `scripts/generate-sw.ts` — post-build: copies the Workbox runtime libs (`workbox-*.prod.js`) and injects the precache manifest (`injectManifest`) into `scripts/sw.template.js`, writing `sw.js` (route/asset HTML/JS/CSS/JSON precache + navigation network-first caching with offline fallback to route shell or root) into `dist/client/`.
- `public/fixtures.json` — real generated data (CI via `scripts/provider/index.ts`; placeholder fallback copied from `data/fixtures.example.json`). Used by development and production builds.
- `public/fixtures.mock.json` — test-only mock fixtures generated by `e2e/run.ts` (`VITE_FIXTURES=mock`); never touches the real file. Selected by `src/lib/loadFixtures.ts`.
- `public/crests/` — self-hosted team crest images (WebP) generated by `scripts/provider/index.ts` (same-origin, never fetched from Football-Data's CDN at runtime).
- Competition codes come from each provider's `defaultCompetitionCodes` (overridable via the `COMPETITION_CODES` env). The default selection (top-5-league teams ∩ UCL) is derived at runtime from the loaded teams by `src/lib/selections.ts` (`defaultBigTeamIds`), falling back to a roster prefix when no such teams exist.
- `.lighthouserc.json` — single shared Lighthouse CI config (assertions + temporary public storage upload); the parallel `lighthouse` matrix selects desktop vs mobile via a per-preset CLI setting — desktop `--collect.settings.preset=desktop`, mobile `--collect.settings.formFactor=mobile` (env overrides are unreliable here: `LHCI_*` keys are camelCased by yargs, so `FORMFACTOR` would set `formfactor`; and `preset=mobile` is rejected by the Lighthouse CLI).
- `scripts/lighthouse-summary.ts` — post-deploy Lighthouse runner: prints desktop + mobile score tables (with per-route report links) to the workflow run summary.
- `vite.config.ts`, `tsconfig.json`, `package.json` — build/tooling configuration (Tailwind via `@tailwindcss/vite`; `components.json` configures the shadcn-style `ui/` components).
- `.pr_agent.toml` canonical PR Agent config (model `openai/mercury-3`, fallback disabled, 32000 max tokens, English responses, `handle_push_trigger` + `push_commands=["/describe","/review","/improve"]`, full reviewer-guidance set, committable code suggestions, AI title + labels). It is the single persistent config source. The action reads repo settings from the **default branch**, so this file is only effective post-merge; while a config PR is open, `main` still holds the prior file.
- **Config is mirrored as workflow env vars** (`pr-agent.yml` env block) under `SECTION__KEY` naming (e.g. `CONFIG__MODEL`, `PR_REVIEWER__REQUIRE_RISK_ASSESSMENT`). Per PR-Agent docs, environment variables take precedence over `.pr_agent.toml`, so the env block is the **authoritative pre-merge config** — it guarantees the running action uses the same values that will apply post-merge. `OPENAI__API_BASE` / `OPENAI__KEY` must stay in env: provider endpoint/auth settings are host-controlled and ignored in repo-local `.pr_agent.toml`. Keep the env mirror in sync with `.pr_agent.toml`; if the TOML changes, update the matching env keys. (After merge, the env mirror could be trimmed to the host-controlled keys, but the full mirror is kept by convention as belt-and-suspenders.)


- **Model is a repo variable**: `CONFIG__MODEL` reads `${{ vars.PR_AGENT_MODEL || 'openai/mercury-3' }}` — the GitHub Actions variable `PR_AGENT_MODEL` (repo-level, host-adjustable without a code change) is authoritative at runtime; the `.pr_agent.toml` value is the fallback default and the canonical post-merge source. Keep all three in sync when the intended model changes.
## Runtime/Tooling Preferences
- **Runtime**: Node ≥ 26 (current LTS; native TS type-stripping runs `scripts/provider/index.ts` without a transpile step; no `engines` declared).
- **Package manager**: npm.
- No path aliases configured; Vite handles module resolution.
- **Vitest**: no config file — runs on defaults. No coverage tooling configured.

## Testing & QA
- **Framework**: vitest; tests are colocated next to source (`*.test.ts`).
- Keep pure logic unit-tested with small data factories; assert with `toEqual`/`toBe`.
- **CI**: PR workflow checks that the PR body contains the required template headings. Deploy workflow runs a Lighthouse performance gate (desktop + mobile, all routes) against the published GitHub Pages origin and posts results to the run summary.
